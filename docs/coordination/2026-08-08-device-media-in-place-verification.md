# Device media in-place verification

## Outcome

Quipsly can now bind a user-authorized Mac folder's exact Insta360 package members into the canonical media graph without copying, uploading, renaming, or exposing a local path. This closes the identity gap between lightweight browse media and the original INSV members needed for later conform and render.

The product deliberately reports two independent states:

- **Source identity**: every required package member has a stable byte size and SHA-256 receipt, and the complete camera package is bound as a `StudioMediaSourceSet`.
- **Browse availability**: an LRV companion has been retained and can proceed through proxy, visual-map, waveform, and transcript preparation.

Neither state implies final-render availability. A render executor must still resolve an authorized original or an explicit exact replica at conform time.

## Trust boundary

The Mac app receives relative observations only after the user explicitly grants a folder. It resolves each candidate beneath that security-scoped root, rejects unsafe relative paths, symlinks, and non-regular files, and then:

1. snapshots file size and modification time;
2. streams SHA-256 in 4 MiB chunks with cancellation and progress;
3. reads best-effort duration, dimensions, and frame rate;
4. confirms size and modification time did not change during verification;
5. sends a path-free receipt to Nest.

The receipt contract rejects path-like top-level fields. Nest validates ownership, active device grant, exact observation key, external reference, revision, byte size, source-unit membership, and source role before recording the receipt. A conflicting checksum is refused rather than overwritten.

## Canonical binding

Once every present member of an observed source unit has an exact checksum and byte size, Nest creates or reuses the deterministic `insta360-360` source set:

- the LRV member supplies the source clock;
- INSV originals are required for render;
- the LRV is explicitly not required for render;
- every member retains its canonical source revision;
- provenance records that bytes were verified in place and that paths were withheld.

The verification workflow job is durable and idempotent. Repeating an identical receipt reuses the same job and source-set identity. Existing exact-replica evidence is preserved rather than weakened to in-place-only evidence.

## Product behavior

Quipsly Studio now presents separate operations:

- **Verify source bytes** reads all eligible package members in place and may be paused.
- **Prepare browse media** retains only eligible LRV companions for navigation artifacts.

Nest shows exact verified members and complete immutable package sets beside browse-pipeline health. An empty or not-yet-followed folder never displays completion language.

## Acceptance evidence

- Receipt contract: malformed checksums, zero sizes, invalid technical metadata, and path-bearing payloads are rejected.
- Database integration: a two-member INSV/LRV package was observed; the LRV was prepared as a browse replica; the INSV was verified in place; a complete two-member source set was produced; the LRV became the clock; the original retained zero replicas and no path was returned.
- TypeScript typecheck passes.
- The signed macOS target builds with the repository-owned automatic-signing settings and an Apple Development identity for team `585GUXMY5M`.
- The signed app was opened and the distinct verification and browse-preparation controls were inspected in the production-details surface.

The acceptance fixture uses generated bytes and database records. No multi-hundred-gigabyte real source folder was hashed during this slice, and no original was copied or uploaded.
